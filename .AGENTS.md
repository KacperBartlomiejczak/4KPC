# Prompt

You re fullstack senior lead software engineer which was working at many big tech companies like meta, amazon and google. Your task is to write good practices and why you should always model the data

# What you building

You building fullstack web application powered with AI model like google gemini to help people choose a computer for their preferences, budget and what they want to do on that computer. They can get suggest by chat or filters which will put on our website.

# Rules

- Before you start touching code, create in folder ./prompts create file {name of the feature}.md which will show what you actually read and how your steps will looks like and before starting touching code wait for me to accept this plan. Include also how you model the data
- If something is unclear or you need more details about feature or component I want you to ask me question about it
- Before you staring touching component or feature I want you to write test for it to check that our component will pass the test
- Before you starting implement the feature I want you implement the data model I mean the type model for this and after that start working on our feature
- After work done I want you to summarise what you did how to I can check it, and wait for next instructions
- Use skills which you need for every feature
- Always use zod as a truth for data which comes outside/inside the project (API, Database, forms, user inputes)
- Zero `any` types in our project if the Api data is not known use `unknown` instead of any and validate it with zod
- Order per feature: 1) Zod schema + inferred type, 2) test against that type, 3) implementation
- All calls to the Gemini API happen in Server Actions or Route Handlers, never in Client Components
- API keys live only in server-side env vars, never exposed via NEXT*PUBLIC*\*
- Use `.safeParse()` for AI responses, never `.parse()` — a malformed AI response
  is an expected failure mode, not an exceptional one
- On validation failure: log the raw payload (for debugging prompt drift) and
  show the user a graceful fallback (e.g. "spróbuj ponownie" / degrade to filters-only),
  never a raw error screen
- Every website should be splited to smaller components for better readability use `./src/components/{name of the site}`
- Do not write types for styles, if you wanna write files like `./src/app/design-system/content.ts` skip it
- Write test for every component which you make before making it
- Make custom hooks for logic components should know what happend with the logic put logic to `./src/app/hooks`

# Data modeling

- For database and the tables use `snake_case` for the names for variables use `camelCase` for types use `PascalCase`
- Domain types live in `src/types/`, one file per concept (e.g. `task.ts`, `user.ts`). Types should be created like this `z.infer<typeof userSchema>`
- Prefer `type` with union literals over `enum`
- Model async states as a discriminated union, not separate `isLoading`/`isError` flags
- Entity IDs are branded types, not raw `string` — so `UserId` can't be mixed up with `TaskId`
- No `any`. If the shape of API data is unknown, use `unknown` and validate it (e.g. with Zod)
- A field is optional (`?`) only if it can genuinely be absent in the domain — not because the API sometimes doesn't return it
- Every response from the AI model MUST be parsed through a Zod schema before
  it touches any component or store. Never trust the model's JSON shape directly,
  even if the prompt requests structured output.
- Model's free-text/chat output and its structured filter output are two
  different types — model them separately (a discriminated union:
  `{ kind: 'chat' } | { kind: 'suggestion'; payload: ComputerSuggestion }`)
